# 管家连续对话与综合归因（需求 53、54）

来源：宠析需求池第 56、57 行，2026-11-13 revision 1210。

需求 53 解决分别分析 A、B 后无法引用“前面两款粮”、跨话题后无法继续、追问与当前背景脱节的问题。需求 54 在此基础上，把用户的实际陈述、前面的产品分析和知识资料组合成有依据的综合回答。

## 实现

- `guardian_conversation_context` 在服务器读取当前用户、会话下的最近 40 条消息，并维护带用户/会话/宠物边界的版本化记忆。记忆保留最多 20 个产品身份、最近对话、6 个健康知识话题和12条饮食/健康相关用户陈述，总记录最多54条。它是有界的上下文，不承诺无限历史记忆；无法确定对象时要求明确名称。
- 旧会话可从已有消息恢复，新消息同时保存结构化来源。产品以 `formula_id` 定位，再读取当前有效画像；不会把“前面两款”当作商品名称搜索。讨论过两款时直接比较；多于两款且指代含糊时确认对象，不任意挑选。
- 相关追问通过语义判断区分继续、回到旧话题、比较、综合归因与新话题。新话题继续走现有业务流程；紧急情况、明确业务操作和具体配料证据入口保持优先。
- 综合归因输出结论、最多3条带消息来源的理由、待补充信息及3个后续问题。明确区分用户陈述、结构评分、未核验知识与模型推测。用户纠正优先；先前的综合推测不会作为独立证据再次引用。来源、结构、长度和明显危险断言校验失败时说明暂时无法核对。
- 健康、产品报告、知识卡片的追问结合当前回答及最近背景生成，生成失败保留原有问题。问题以主人向管家提问的口吻生成，并随回答保存，历史回读不重新生成。
- 小程序追问携带 `source_message_id`；服务端校验原消息归属和原问题内容，禁止跨会话、伪造或失效来源。综合回答复用普通正文展示，增加三个追问按钮；旧客户端继续读取普通正文。
- 修正原场景识别入口的紧急症状检查顺序：即使客户端未上报新能力、已有待确认流程，也优先风险分诊。

不新增数据库表或字段，复用 `miniprogram_chat_state.slots_json` 和消息 `result_json`。不自动修改实际吃粮记录，不在本需求中改变营养算法、知识采集或生产上的其他未提交改动。

## 验证与发布

- 新增20个后端用例，覆盖跨轮产品定位、长期保留、作用域和来源校验、语义返回话题、伪造模型引用、综合证据、失败降级、完整路由、画像缺失及紧急情况。
- 扩展回归389项通过、26个子用例通过。23项失败与 `4a36c7d` 独立基线相同；基线369项通过。既有失败涉及撤下的推荐入口及旧推荐期望。
- 隔离 MySQL 和 Flask 接口使用真实认证、消息持久化和模型，验证“健康问题→分别分析两款粮→引用前两款比较→综合归因→点击旧卡片问题→风险分诊”。回读结果一致，伪造/跨会话来源返回400，未认证返回401。产品目录使用已验证的实际数据快照作为固定夹具，报告查询使用复制后的实际画像；社区召回和旧高低档映射不在此验证范围。
- 前端自动检查验证问题渲染、历史映射、未知版本回退、发送防重、宠物边界及原消息标识。
- 微信工具联调固定复用 `local-dev/qa34-miniprogram`。使用真实接口结果渲染综合结论及追问、旧健康卡片和比较报告；事件验证采用官方自动化 SDK，测试时拦截发送处理器，不向生产发消息，也不改登录存储。

测试记录及截图位于工作区 `local-dev/qa53-54`。部署时先备份并校验服务器其他任务的未提交文件，再快进代码，只重启本应用；小程序走 PR 发布流程。
