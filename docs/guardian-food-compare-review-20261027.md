# 对话内「对比粮」与风险模型接入复盘（2026-10-27）

针对两个反馈：① 对比结果看起来都差不多；② 对比时似乎没用风险模型。
排查范围：`guardian_product_portrait_service.py` / `guardian_recommendation_service.py` /
`guardian_food_flow_service.py` / `guardian_food_analysis_service.py`，
数据取自 `protein_feature_platform`（只读）。

## 一、对话里的"对比"到底比了什么

`compare_portraits()` 只读 5 个结构分，输出固定三段：共同特点 / 可补足的方面 / 潜在短板。

```
蛋白压力(protein_score) 脂肪负担(fat_score) 纤维支持(fiber_score) 碳水负担(carb_score) 益生元支持(prebiotic_score)
```

判定阈值（`guardian_product_portrait_service.py:129-139`）：

| 判定 | 条件 |
|---|---|
| 结构接近 | 归一后 `abs(Δ) ≤ 0.10` |
| 可补足 | 负担类 `Δ > 0.10`；支持类 `Δ > 0.10 且 new ≤ 0.75` |
| 潜在短板 | 负担类 `new > 0.65 或 Δ > 0.10`；支持类 `new ≤ 0.25 或 new > 0.75` |

## 二、为什么"都差不多"——数据层面就分不开

全库 `sku_feature_input` v1 只有 **121 个配方**（去重后），五维分布：

| 维度 | 归一后区间 | 均值 | SD | 两两「接近」占比 | ≤0.25 占比 |
|---|---|---|---|---|---|
| 蛋白压力 | 0.15 – 0.70 | 0.54 | 0.084 | **64%** | 1% |
| 脂肪负担 | 0.10 – 0.69 | 0.36 | 0.106 | 49% | 17% |
| 纤维支持 | 0.00 – 1.19 | 0.49 | 0.285 | 18% | 23% |
| 碳水负担 | 0.00 – 1.05 | 0.46 | 0.221 | 25% | 17% |
| 益生元支持 | 0.00 – **0.44** | 0.20 | 0.123 | 42% | **63%** |

两个硬伤：

1. **归一化基准和真实值域不匹配。** `DIMENSIONS`（`guardian_food_scenario.py:11-17`）把
   `prebiotic_score` 的 scale 定为 5，但全库实际最大只有 2.18，归一后天花板 0.44 —— 于是
   **63% 的配方必然被判"益生元支持偏低"**，任何对比的"潜在短板"都长一个样。
   蛋白同理：全库最高 0.70，永远够不到 0.75 的"偏高"线，所以"蛋白质量评价较好"是常量。
2. **阈值相对 SD 太宽。** ±0.10 对 SD 0.084（蛋白）意味着 64% 的两两组合都算"接近"。

结果：任意两款粮，结论必然是「蛋白压力接近 + 益生元偏低 + 脂肪/碳水更低」。今天 07:16
那条换粮对比就是标准输出：

```
共同特点：两款粮的蛋白压力结构接近（0.607 / 0.558）
可补足的方面：目标粮的脂肪负担比原粮更低…；目标粮的碳水负担比原粮更低…
潜在短板：目标粮的蛋白质量较高，不能视为越高越适合…；目标粮的益生元支持偏低
```

附带两个观感问题：
- 同一段里「蛋白压力接近」和「蛋白质量较高」并列，两个维度名字太像，用户读不出区别。
- 该条还出现「原粮或目标营养资料不足，暂不能做数值对比」——保证值透视在原粮侧就断了，
  数值对比直接失效，只剩结构分。

## 三、推荐列表更薄：只有两个数字 + 一句免责

`10:50:18` 三条候选的实际渲染：

```
✅ 入选依据：脂肪负担参考分0.335→0.28；碳水负担参考分2.5→0.6
适用阶段：全阶段
❗ 本次按配方结构筛选，未核验能量密度；不据此认定减重效果。
```

- 没有 `fit_score`，用户看不到排序依据；
- 三款候选的免责声明、句式、字段完全一致；
- 07:16 那次（参考粮 皇家 FR31）与 10:50 那次（参考粮 蓝氏猎宴火鸡）**3 个候选里有 2 个完全相同**
  （网易严选 冻干双拼乳鸽、喜喵 鲜蒸），换参考粮只换了第 3 个；
- 07:16 那次两个不同产品给出了完全相同的数字（鲜朗 0.481→0.186、喜喵 0.481→0.186）。

## 四、风险模型：对比没用，换粮方案也没渲染

风险模型有数据，也确实接进来了，但接的位置很偏：

| 位置 | 是否用风险模型 |
|---|---|
| `compare_portraits`（粮对粮对比） | **完全不用**，只读 5 维结构分 |
| `analyse_food`（单品分析 payload） | 用，`risk_models` 来自 `load_risks` |
| `guardian_food_flow_service.py:276`（"已选定"分支） | 渲染为「软便结构风险参考：xxx」 |
| `guardian_food_flow_service.py:283+`（**换粮方案分支**） | **没有这个循环**，只有一句 `risk_note` |
| 对话 LLM 提示词 | 未要求引用 `risk_models` |

数据源：`protein_feature_platform.sku_risk_score_result`，452 行 / 125 个配方 × 2 个模型
（`SOFT_STOOL_*`、`BLACK_CHIN_*`）。这两个模型对同一对粮给出的结论是能分开的：

| 配方 | 软便模型 | 主因标签 | 黑下巴模型 |
|---|---|---|---|
| 蓝氏 猎宴火鸡全价猫粮（6） | **中高软便配方风险** | 碳水结构压力偏高 | 中低配方风险 |
| 鲜朗 兔肉烘焙猫粮（25） | **低软便配方风险** | 菌群代谢支持不足、肠道缓冲支持不足 | 中低配方风险 |

这两个结论在今天所有对话里**一次都没出现过**。用户在 07:22 看到的
「软便、胀气：益生元支持偏少」是纯特征推理，不是软便复合风险模型的输出。

参照：内部 B2B 工具 `consumer_apps/product_compare_qwen.py` 是接 `sku_risk_score_result`
的（`risk_table` 配置在 72 行），也就是说**同一个公司两套对比，一套有风险模型一套没有**。

## 五、建议改动（按性价比）

| # | 改动 | 落点 | 预期效果 |
|---|---|---|---|
| 1 | 换粮方案分支补 `risk_models` 渲染（照抄"已选定"分支的 276 行） | `guardian_food_flow_service.py:283+` | 对比立刻带上软便/黑下巴风险等级，改动最小 |
| 2 | `compare_portraits` 增加风险模型差异作为第 6 维度 | `guardian_product_portrait_service.py:121` | 对比有真正能分开两款粮的信号 |
| 3 | 修归一化 scale：`prebiotic/fiber/carb` 改按实际值域或分位数归一，阈值改按 SD（如 ±0.5 SD） | `guardian_food_scenario.py:11-17`、`portrait_service.py:129` | 消除"全员益生元偏低" |
| 4 | 候选卡片输出 `fit_score` + 一条差异化理由（用已有的 `strengths`/`current_food_reasons`） | `guardian_recommendation_presentation.py` | 三条候选不再长得一样 |
| 5 | 提示词显式要求引用 `risk_models`，并把「蛋白压力 / 蛋白质量」改名区分 | 分析类 system prompt | 结论不再互相打架 |
