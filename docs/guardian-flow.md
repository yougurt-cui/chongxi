# 管家流程：定位与扩展

## 本次定位

围绕宠物档案、当前饮食、历史吃粮表现和健康背景，提供饮食分析、行动建议与持续跟进。不给诊断结论，不要求用户完成症状问卷。用户主动提供明显风险表现时保留就医提示。

软便默认顺序：**当前粮 → 历史粮表现 → 健康背景 → 综合建议**。已有资料先用；缺少当前粮才问名称；实际发生饮食变化才补问相关细节。每个背景步骤最多问一次，未知或未回答也能收尾。

首次展示产品证据与机制，后续展示新增事实、解释和下一步。最后给行动、观察、复评，并保留继续选粮的入口。

## 策略与分支

- `FlowStrategy` 统一 `matches(message, state)`、`handle(...)` 接口；`GUARDIAN_STRATEGIES` 是代码中的策略实例列表，不是 MySQL 表。
- 每轮先识别需求，再选择策略；目前注册软便、选粮衔接、通用对话三个策略。
- 策略内部通过 `Step` 组合步骤：声明名称、所需字段、问题与进入条件。新增案例分支增加步骤或条件；新增独立场景注册策略，避免修改聊天入口的业务分支。
- 公共入口负责认证、消息顺序和存储；策略负责更新自己的状态并返回统一的回复结构。

现阶段配置在代码中、随版本测试发布。以后需要运营配置时，再增加后台、版本校验与回放能力，不直接执行数据库中的任意条件代码。

## 识别与切换

明确的选粮请求、既有话题切换及短答先用规则。软便原有的 LLM 信息抽取同时返回 `dialogue`（动作、目标场景、置信度与本轮原文依据），不额外调用一次路由模型。置信度不足不强行切换。复杂否定表达本期不全面覆盖。

选粮中回答“希望改善软便”是选粮偏好，不能因为出现关键词就重新进入软便流程。

切换时保留原策略进度，生成 `_guardian_context`：宠物信息、当前粮、历史与健康背景、已确认字段及来源、分析摘要、缺失资料。目标策略复用这些信息，只补自身缺少的条件。
