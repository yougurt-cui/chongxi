# 软便任务测试说明

当前反馈修复在 `feature/guardian-feedback`。无需新增数据库表；状态、事实来源和版本保存在现有聊天 JSON 中。架构见 [管家流程](guardian-flow.md)。

## 已实现

- 每轮两条回复：后端生成事实卡；机制解释、补充问题或行动建议。首轮展示配方，后续只展示新增信息；资料有限提示只在最终解释显示一次。
- 主粮、罐头、零食分别识别；当前粮与原粮分开，用户纠正会更新上下文。
- 按当前粮、历史粮表现、健康背景推进；实际饮食变化才走细节分支，不要求回答症状问卷。背景步骤最多问一次；未知不当作否认，资料有限也给建议。
- 伴随风险先于产品查询；缺表、缺保证值和模型故障可降级。营养差异只比较同口径的标示保证值。
- 对话途中可进入选粮或其他模块，保留原流程并传递已知信息；合并信息抽取和切换识别，不增加独立路由模型调用，短答不调用抽取模型。
- 模型字段必须附本轮原文依据；不默认填持续时间 0。恢复旧状态时清除缺少原文依据的旧版零天值；模型降级记录原因，不记录密钥或完整错误正文。

## 本地接口联调

本机独立 MySQL 需要运行，配置为 `127.0.0.1:13306`、`chongxi_dev`。执行：

```bash
.venv/bin/python -B scripts/smoke_soft_stool_local.py
```

脚本只允许连接上述本地开发库，通过 Flask 测试客户端执行真实 API、认证、宠物归属和聊天存储；产品和模型使用离线替代。检查三轮咨询、消息顺序、途中选粮及上下文、含“软便”的选粮偏好、暂停恢复、风险优先与未登录访问；清理临时测试用户。无需启动额外 HTTP 服务。

## 真实模型和前端联调

需补开发模型 Key，以及产品、配方评分和参考池开发数据。用接口调试工具调用本地服务，带本地用户 `Bearer token`，先创建宠物档案及会话，再连续发送消息：

- `POST /api/miniprogram/chat/conversations`，请求 `{"pet_id":"测试宠物ID"}`。
- `POST /api/miniprogram/chat/conversations/{会话ID}/messages`，请求 `{"message":"用户的话"}`。
- `GET /api/miniprogram/chat/conversations/{会话ID}/messages`，检查历史记录。

| 场景 | 验收预期 |
|---|---|
| BK34 软便咨询 | 数值取自开发数据；碳水、蛋白等机制按规则解释，不确定因果 |
| `软便了 → 没有 → 没有` | 问历史粮、健康背景后给建议，无虚构零天，无必答症状问卷，无整段机制重复 |
| 没换主粮但加罐头；连续短答 | 记录添加事件；“没有”只回答上一问，不误记成没有饮食变化 |
| 饮食变化晚于软便；修改当前粮 | 保留时间反证，刷新当前产品证据，不保留旧比较结果 |
| 产品缺数据、模型异常、伴随风险 | 不编造数据；风险回复不依赖产品查询和模型 |
| 途中选粮或其他模块 | 能切换并复用事实来源；选粮偏好中的“软便”不会重启咨询；可恢复原流程 |

病历补充动作通过 `message.result.actions` 提供：`{"type":"medical_record","label":"补充病历","pet_id":"…"}`。最终建议可提供 `flow_handoff` 选粮动作。前端需展示并衔接入口；本次未修改小程序 UI。完整产品排序与品牌推荐尚未接入。

离线测试通过不代表真实 LLM 回复质量或生产 BK34 数据已验收。并发幂等、完整历史事件和可配置临床风险分级仍属后续工作。
