# 需求 23：产品健康解读与推荐分阶段

用户询问当前粮、历史粮、具体产品或提交已解析的投稿时，管家先展示有来源的营养健康解读。用户选择需要推荐后，携带该次分析进入原有选粮流程；选择暂时不用则保留分析，可继续追问。

产品确认：中间档暂不处理；用户直接要求推荐且没有当前粮时，沿用已有流程。本次也保留已有直接推荐入口，不新增强制补当前粮步骤。未实现第 22 项独立的产品分析健康问询。

## 数据与解释

- `guardian_health_analysis_service.py` 读取现有 `catfood_nutrition_factor_health_mapping` 的 `v1`、`active` 数据，保留映射编号、原关注点、知识版本和审核状态。
- 现有导入数据全部为 `pending`；本次按产品提供的有效映射接入，允许 `pending/approved`，排除被拒绝和停用记录。`pending` 不代表临床审核通过，本次没有变更任何记录的审核状态。
- 使用已通过来源与版本校验的 `six_dimension_v2` 产品画像；只匹配画像原有 `high/low`，不新设阈值，不将缺失或中间档折算成低档。
- 多个因子按健康关注点归并，例如软便、便秘、便便稳定归为便便状态；机制和观察事项均来自命中的知识行，不由模型补写。
- 优先用户明确反馈的相关关注点，再按观察类型、覆盖维度数和稳定名称排序，最多三项。证据不足时可以少于两项。
- 映射未设置 `relation_type` 时，明确的软便、便秘、胀气关注点以及高负担/低支持标为重点观察；其他高支持为配方优势参考，低负担为常规观察。已有显式 `attention/advantage/routine` 类型优先。
- 画像、知识或具体映射不可用时，返回明确降级状态，不用通用模型补健康结论。产品比较仍使用现有画像比较证据。

## 会话与协议

沿用 `/api/miniprogram/chat/conversations/{id}/messages`，不新增 API。既有文字客户端可继续读取完整 `content`，新版客户端读取结构化卡片。

```json
{
  "response_type": "result_card",
  "interaction": {
    "slot": "food_health_recommendation",
    "analysis_id": "服务端生成的分析标识",
    "options": [
      {"label": "需要推荐新粮", "value": "yes:服务端生成的分析标识"},
      {"label": "暂时不用", "value": "no:服务端生成的分析标识"}
    ]
  },
  "result": {
    "intent": "food_analysis",
    "analysis_id": "同一分析标识",
    "analysis_stage": "pending",
    "food_candidates": [],
    "health_analysis": {
      "version": 1,
      "subjects": [],
      "comparisons": [],
      "prompt": "是否需要根据上述内容推荐新粮？"
    }
  }
}
```

每个 subject 包含产品名、配方 ID、状态、关注点、缺失维度和知识/画像来源。每个关注点包含标签、画像依据、机制、观察事项及映射来源。对比使用两侧相同结构，并补充现有画像差异与取舍文本。

点击时原样回传服务端选项 `interaction.slot/value`，新版客户端另传 `analysis_id`。分析身份编码在选项值中，因此旧客户端也能安全消费新选项，不需要丢弃旧按钮校验来做兼容。两处 ID 同时存在时必须一致。自然语言确认由服务端绑定当前分析，也接受带独立 ID 的 `yes/no`。

服务端校验分析 ID、账号、宠物、会话及待确认阶段；新分析、其他话题、拒绝或已消费的确认使旧操作失效，不能重复触发召回。简短明确的“需要”“暂时不用”等文字也支持确认；不确定或询问语句不作为同意。

状态快照保存在原有会话状态 JSON，完整报告同时保存在聊天消息 JSON，无需新增业务表。确认后保留 `health_recommendation_context` 供后续轮次解释；既有召回继续负责筛选和排序。历史粮或上传粮不会被写成当前粮，分析和推荐也不会更新实际吃粮记录。

同名产品或多个配方版本不默认选第一项，而是返回 `food_analysis_catalog` 选择；只接受当前服务端提供的选项。历史粮仍受现有有效配方读取规则约束，不新增历史时点旧版配方还原。

## 验证与运行

```bash
.venv/bin/python -m unittest discover -s tests
```

`tests/test_guardian_health_analysis.py` 覆盖高低/中间/缺失档、来源与版本、归并、当前/历史/上传/对比、确认与拒绝、跨用户/宠物/会话与旧按钮、自然语言确认、追问和无当前粮推荐。原聊天测试已改为验证有依据的报告，不再期待模型生成产品健康结论。

还在仅监听回环地址的本地 MySQL 中，用真实目录、119 份六维画像和 21 条现有映射完成鉴权/API/聊天历史持久化联调：分析和对比不召回、确认后原召回可返回候选、上传粮不覆盖当前粮、无当前粮保留原流程。通用推荐语言整理在该 API smoke 中使用确定性替身；健康映射、画像、召回、鉴权和数据库持久化使用实际实现。

部署前确认目标库已有有效六维画像和上述映射表。缺表时分析会降级，不会在聊天请求中建表或重建画像。需要数据准备时，沿用原导入与画像重建工具。本次仅改本地代码和本地测试数据，未部署生产。
