# 需求34：管家接入本地知识库

已有软便咨询、选粮/换粮、产品/原料分析、状态解读、提醒及交互按钮、上传附件仍使用原有处理器。仅识别为 general_pet_qa 的普通提问接入新链路：

1. 从已认证会话取得宠物ID，通过 get_cat_profile 校验归属。
2. 加载档案、最近10条吃粮记录和最近14天 pet_metric_anomaly；健康库沿用 PET_HEALTH_DATABASE_URL / pet_health_models.get_db_url 配置。只读，不创建表、不分析设备、不写记录。区分无记录和读取失败，保留真实的0值。
3. 用当前问题、连续追问和已知物种/年龄构造关键词及话题条件；沙发/磨爪、新家/新环境、喝水/饮水等作同义扩展。明确问其他物种时，不套用当前宠物的年龄等个体信息。追问仅沿用同一宠物且中间未经过其他流程的知识查询。
4. 参数化查询 `kd_problem_guides`，按问题、症状、原因/办法、风险及争议字段的匹配数量排序，最多取300条候选；按物种、生命阶段和其他适用条件过滤并去重，最终最多5张知识卡。不再回退读取 `knowledge_base`。
5. 将档案/饮食/近期异常与命中知识卡交给当前聊天模型判断资料是否充分，并选择最多3张能够直接回答问题的知识卡。返回 guide ID 和完整知识卡正文，逐字校验，不允许编写来源外的新事实或删去否定/适用条件。正文按现有聊天文本和 display_blocks 展示。

知识读取只依赖二次蒸馏结果表 `kd_problem_guides`，不导入蒸馏 writer、不执行 ensure_tables，也不变更审核状态或原始知识数据。

## 资料边界

当前线上知识多数仍是“待审核/待验证”。允许其低中风险日常照护内容作为社区资料参考，回答固定附上“尚未专业验证”的提示；排除被拒绝、无来源、有争议、有反证、高风险未专业审核内容。未验证资料中的用药/剂量、医疗结论和具体数字护理频次不召回。知识中的提示词指令也不作为指令执行。

未知物种、年龄或其他适用条件不猜测，条件不明的受限知识不使用；未知的附加限制不会被静默忽略。不把健康异常当疾病、不将无记录当正常、不凭知识库改已有选粮排序或推荐流程。

玩耍等已识别主题必须命中相应核心词，不能仅凭“不爱”等泛词召回挑食资料；选购问题只召回选择标准。无匹配或模型判定资料不足时说明不足；知识库不可用时提示稍后重试；模型不可用、JSON无效、来源ID越界或原文被篡改时，仅展示实际命中的少量原文资料及证据等级，不使用原有通用疾病兜底。

## 接口与运维

沿用 POST /api/miniprogram/chat/conversations/<id>/messages，不新增前端请求字段或页面。返回 result.pipeline=knowledge_qa，result.knowledge_qa 包含检索状态、生成方式、查询主题、实际采用的知识ID、审核/证据等级和上下文读取状态；不返回私人原始档案、吃粮明细或健康记录。元数据随消息保存，历史回看可追溯。

无需新增依赖或数据库迁移。服务模块为 guardian_knowledge_service.py，只有新兜底入口调用。保留线上尚未提交的知识清洗、健康库配置改动；部署前后核验这些文件摘要不变。

验证覆盖：旧流程路由隔离、物种/年龄/未知条件、来源与风险过滤、SQL参数化、追问范围、0/无记录/不可用、健康记录归属与时间范围、模型失效/虚构来源ID，以及真实API持久化和线上只读知识试答。
