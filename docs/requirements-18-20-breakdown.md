## 2. 第 18 项：自动解析

### 已有什么

- `services/miniprogram_food_submission_service.py:create_food_submission`：保存照片、创建 `catfood_image_analysis` 任务，并直接回报 `upload_check` 成功。任务 payload 已保存 `submission_id` 和投稿用户 ID。
- `services/orchestrator_service.py`：已有任务、节点、结果持久化；依赖满足后置为 ready，执行回报后校验结果、推进下一节点及判断任务终态。
- `api/orchestrator_api.py`：已有 `/dispatch-claim`、`/tasks/{task_id}/nodes/{node_code}/result`、手动重跑及同步调度接口；管理接口使用管理鉴权。
- 最新代码已有 OCR 瞬时错误重试。该重试解决单次 OCR 请求的一部分网络问题，不等同于整个任务断点恢复。

仓库定义实际为 **12 个节点、11 个配置了 API 的节点、11 个不同 URL**，与需求中的“8 个业务 URL”有差异。依赖关系决定是否能运行，priority 决定就绪节点的先后，不应仅按数字遍历调用。

```text
upload_check → ocr_formula → brand_standardize → formula_precheck
→ product_standardize → formula_standardize → formula_input_build
→ ingredient_extract → science_feature_materialize → ingredient_standardize
→ formula_profile → market_profile_build
```

### 目前缺什么、为什么不能只加定时器

| 已核实的代码事实 | 对自动化的影响 |
| --- | --- |
| 当前检出的仓库没有 `orchestrator_runner.py`，也未找到对应常驻服务配置 | 需要补执行器及部署管理；生产是否另有仓库外脚本尚未核实 |
| 认领先读取 ready，再无条件写 running，没有 claim token、租约及原子状态条件 | 两个执行器可能重复认领；进程退出后节点可能一直 running |
| 回报没有执行轮次令牌校验 | 超时重跑后，旧请求的迟到回报可能覆盖新状态；撤销与回报也需统一处理 |
| 回报为 failed 后，任务会退出普通扫描；need_review 同样暂停自动推进 | 需要区分可重试故障、真实业务失败和人工复核，不能无限重试 |
| `upload_check` 没配置业务 URL | 投稿入口已完成此节点；其他创建入口仍需明确服务端本地检查方式，不能跳过校验或反复认领空 URL |
| 扫描先截取 `limit * 5` 个任务，再找 ready 节点 | 较多长期运行/等待输入任务可能占满扫描窗口，需要避免后续就绪任务被饿死 |
| 最后节点执行全市场排名、结构标签及画像重建，已有全局 MySQL 锁 | 每份上传都触发重计算；锁冲突目前抛异常，不能直接当产品处理失败 |
| 一个市场重建节点含三个子脚本，各自可等待 1200 秒，而节点 API 标称 1200 秒 | 外部执行器的调用超时、租约和重建实际耗时需要对齐，HTTP 超时不代表服务端已停止 |

### 建议怎么做

1. **提交后唤醒后台 worker**：结合下文进一步核查，首版优先沿用现有“落库后提交后台线程池”的模式，增加专用的有限并发流水线执行器；任务与投稿全部保存成功、提交事务且标记可执行后，发出进程内唤醒信号。后台从 MySQL 认领任务，成功后立即执行下一节点。启动及低频（建议初值 30–60 秒）补扫恢复漏处理任务，先不引入 MQ。进程内唤醒只适用于当前单应用进程方案；如果采用独立进程或多机器部署，应另选跨进程唤醒方式，不能直接共享 Python Event。
2. **可靠认领和回报**：事务内原子认领，记录 `worker_id`、`claim_token`、执行轮次、心跳、租约和重试时间。只接受当前执行轮次的回报；重复回报保持幂等，撤销任务拒绝后续推进。上线前先采用保守并发，再根据实测放大。
3. **恢复与重试**：网络波动和限流按有上限的退避重试；租约到期先判断业务请求是否仍在执行。已产生业务副作用但回报丢失时，先核验结果再决定是否重跑。数据缺失/待审核进入明确等待状态，修正后从受影响节点恢复。
4. **控制重计算**：首版保留现有终态检查，市场重建排队执行，锁忙作为等待处理；后续合并短时间内多个重建请求或引入增量构建。若合并，必须证明每个等待任务对应配方已被该次重建覆盖，不能只通知最后一份投稿。
5. **后台更新投稿状态**：目前 `_sync_recognition` 在用户读取列表/详情时同步 OCR 状态。增加后台状态同步及业务事件，用户离开页面后也能推进展示状态并触发通知。
6. **可观察进度**：展示排队、识别、计算、待核对、完成、失败及失败原因；记录排队时长、分节点耗时、重试次数、积压量和异常量。以这些数据决定下一步优化，避免仅靠调小轮询间隔。

此前“3–5 秒”只是纯轮询方案的发现间隔建议。进一步核查后，改为优先即时唤醒、低频补漏；正常接单无需等待轮询。OCR、评分及全市场重建的实际耗时仍需要实测。

### 进一步核查：数据库、唤醒与 CPU 开销

**已有的基础设施。** `orchestrator_service.init_db` 已定义并初始化 MySQL 表 `pipeline_task`（任务）、`pipeline_task_node`（节点）、`pipeline_node_output`（结果）；节点表已有状态/优先级索引，任务表已有类型/状态及更新时间索引。代码已有存储和建表机制，不需为 18 新搭数据库或重新设计一套任务表，可靠执行所需字段和索引可在原表迁移补充。本次没有连接生产数据库核验实际表结构。

**已有的即时后台执行模式。** `main.py` 有两线程的 `ThreadPoolExecutor`，部分上传入口落库后立即 submit；但 `_parse_uploaded_image_task` 当前是文件入库状态占位，不执行真正 OCR 或后续完整流水线。`market_profile_rebuild_service.create_rebuild_task` 则已有实际可用的模式：先写重建任务表并提交事务，再 `_executor.submit(_run_rebuild, task_id)`。这证明无需为“收到任务立即执行”先部署 MQ；不过它尚未解决整条流水线的持久恢复。

**建议的调度方式。** 增加专用且有容量限制的流水线线程池，避免长时间计算占满现有其他任务线程。生产代码封装启动、唤醒及关闭生命周期；启用实例需明确，开发热重载和多个 Web 进程不可随意重复启动。唤醒只是“去查库接单”的提示，MySQL 才是任务事实来源，信号丢失也有恢复路径。

```text
上传接口：任务/投稿提交成功并标记可执行 → 唤醒后台 → 返回用户
后台：收到信号 → 原子认领 ready 节点 → 执行/回报 → 有后续则继续
空闲：阻塞等待信号；超时才补扫
启动：补扫待执行任务，并核验之前中断的执行
人工修复：状态恢复可执行后再次唤醒
```

执行器自身正在推进任务时，不需要靠唤醒信号完成每个节点。线程阻塞等待期间不忙转，不持续消耗 CPU 进行检查；实际工作和补扫仍有 CPU、数据库与网络开销，并非零成本。

**现有查询实际在查什么。** `claim_ready_dispatch_jobs` 先筛 `task_status IN ('created','processing','waiting_input')` 的任务，再读取任务的所有节点和已保存输出、刷新依赖，最后选 `node_status='ready'`。它不是无条件把所有历史任务交给业务程序，但也不是一次轻量状态查询。`get_task` 每次还会调用 `init_db`、补节点并读取结果 JSON，一轮调度多次调用会放大连接和 SQL 开销。

建议将初始化/迁移移出高频读取路径；补扫分开处理 ready、到期重试及租约过期的节点，普通补扫不反复加载所有等待输入任务和大段结果。只有认领成功的节点再组装输入。查询只取必要 ID，限制批量，并以实际 MySQL `EXPLAIN` 验证索引与排序，必要时补复合索引。认领仍需数据库原子条件，不能只依靠进程内去重。

每 3–5 秒补扫相当于每个调度器每分钟发起 12–20 轮；每轮可能多条 SQL。带阻塞等待且查询合理时，通常不会因这点频率把应用 CPU 跑满，但未做实测，不能直接给出占用百分比。采用即时唤醒 + 30–60 秒补扫能同时减少空查和正常接单延迟。

### 进一步核查：全市场重建为什么存在、怎么优化

当前流水线末节点确实调用三个全量脚本，不是重新读取所有包装图片、重新做全部 OCR 或调用大模型生成文案：

| 脚本 | 实际计算 | 是否依赖全市场 |
| --- | --- | --- |
| `build_module_market_ranking.py` | 读取评分宽表中全部有效配方，用 `rank(pct=True)` 计算百分位并生成优势标签，写回全体结果 | 是；增加配方或修改分值可能改变旧产品百分位 |
| `build_formula_structure_labels.py` | 从蛋白、纤维、脂肪原料特征生成各配方结构标签 | 主要取决于自身特征；当前实现是全量，后续适合按配方增量 |
| `build_formula_profile.py` | 合并标签与排名，计算弱势标签并用规则拼接摘要 | 受全市场排名/分位阈值变化影响 |

只有上传后的前置节点成功、末节点实际执行才触发重建；新增产品名称但还没有有效配方评分，不会直接纳入这套排名。当前实现也没有根据输入特征哈希判断“旧配方重复上传且无变化”就跳过末节点，所以重建触发范围可能大于真正的数据变化。

建议分层推进，不为尚未测量的性能问题先重写算法：

1. 首版保留全量计算，记录参与配方数、三段各自耗时和 CPU/内存、并发投稿的队列等待；修正锁忙时直接失败的问题。
2. 用配方特征/规则版本判断是否真的变化；不变时核验已有产物版本和覆盖率后复用，不能仅凭产品同名跳过。
3. 多个等待重建的投稿可合并同一批次；重建期间新增或变化的数据需要后续一轮或一致快照，不能错误地视为已覆盖。本轮只完成已核实覆盖对应输入版本的等待任务。
4. 需要进一步优化时，先将产品自身结构标签改为增量；全市场排名保留合并重算。若市场排名允许延迟，则把个体结果可用和市场排名更新分开，但这会改变任务终态/通知口径，需同步调整需求。
5. 结构标签当前在一个事务删除全表、另一个事务写回，因此失败时可能留下空表，读取方也可能看到中间状态。保留全量方案也应修复为原子替换/版本化发布，并尽量让排名、标签、最终画像属于同一可识别批次，失败时继续使用上一份成功结果。

这些是代码确认后的设计建议，尚未压测全量重建，也未修改业务实现。

### 画像与未知原料边界

- 当前末节点检查的是市场排名、结构标签和 `catfood_formula_profile`。管家 16、17 使用的五维画像表 `catfood_formula_portrait_summary` 由另一服务维护，当前市场重建函数没有直接调用它。若完成通知要承诺“现在可做管家画像对比”，必须补该画像的更新与版本校验；流水线 done 不能直接证明所有消费端资料都已更新。
- 相邻第 21 项明确提出未知原料先按已有标准化池量化、齐全后二次更新。它直接影响 18 的完成率。仅加 worker，未知原料仍可能让任务等待人工处理。
- 建议提前预留 `processing_status` 与 `result_completeness` 两个独立概念，后续支持“部分结果可用/完整”。若实施 21，需要记录缺失原料、实际覆盖率、计算版本和重新计算依赖，不能把未知原料当作 0 或伪装成完整数据。21 的计算规则属于相邻需求，不在本次分析中擅自定稿。

## 3. 第 19 项：解析完成通知

### 先明确“完成”的含义

现在至少有三个不同事件：

| 事件 | 可以告诉用户什么 | 不能据此声称什么 |
| --- | --- | --- |
| OCR 有效且识别通过 | 配料表已识别，可以查看识别内容 | 全部评分、画像已完成或产品已收录 |
| 业务计算完成并通过结果校验 | 该版本分析结果已可查看 | 自动代表审核通过、产品已发布 |
| 审核通过并发布 | 产品已收录 | 不应与前两个状态混用 |

**建议首版把第 19 项理解为“分析结果可用后的一次完成通知”**，默认在 18 的流水线成功并核验所承诺结果后触发。OCR 识别完成保留页面状态；若业务希望 OCR 即通知，则使用“配料表识别完成”文案，与全流程完成明确区分。这是建议口径，需求原文没有给出最终选择。

### 现状和方案

代码已有关联投稿、用户及微信 openid 的基础；当前小程序未找到 `wx.requestSubscribeMessage` 接入，也未找到解析结果的微信通知发送服务。投稿页每 5 秒刷新识别状态，离开页面会停止刷新，不能替代离线通知。

建议流程：

```text
用户点击“完成后通知我” → 微信订阅授权 → 关联当前投稿
→ 后台结果通过校验 → 写入完成事件/待发送记录
→ 通知 worker 下发 → 点击进入该用户的投稿详情
```

- 前端在用户点击时请求订阅；拒绝或调用失败不阻止上传。订阅授权与当前投稿绑定，处理“结果已完成、授权稍后才到”的竞态。
- 后端以“投稿 ID + 事件类型 + 结果版本”建立业务事件唯一约束；状态落库与待发送事件在同一事务提交，必要时通过补偿扫描补齐。
- 单独处理通知，发送故障不回滚解析任务。已有已确认成功记录不重复发送；网络超时且微信接收情况未知时单独标记待核验，不承诺跨外部接口绝对恰好一次。
- 记录模板、接收人、事件、尝试时间、平台返回及失败原因。临时错误有限重试；拒收或无可用订阅权限不持续重试。站内投稿结果始终可查。
- 通知跳转复用 `/pages/pet-space/food-submissions?id=...`；现有页面已能读取 id。仍需验证未登录恢复跳转和跨账号不可读取他人投稿。
- 示例文案：“你提交的【产品名】分析已完成，点击查看结果。”模板字段、长度和状态枚举须以该小程序后台实际可用的模板为准。

通过 ego-browser 核实的微信官方要求：模板需先在公众平台配置获取；前端请求下发权限，服务端再下发；`wx.requestSubscribeMessage` 限制在点击行为调用。见 [订阅消息指南](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/subscribe-message.html)、[订阅授权 API](https://developers.weixin.qq.com/miniprogram/dev/api/open-api/subscribe-message/wx.requestSubscribeMessage.html)、[发送订阅消息 API](https://developers.weixin.qq.com/miniprogram/dev/server/API/mp-message-management/subscribe-message/api_sendmessage.html)。本次没有进入小程序管理后台确认实际模板 ID、类目及权限，也没有发送真实消息。

## 4. 第 20 项：管家回复样式

### 现状

- 管家主页面 `pages/assistant/index.wxml` 用 `<text selectable>{{item.text}}</text>` 渲染回复，不支持把 Markdown 星号自动显示为粗体。
- `utils/assistant-chat.js:mapChatMessage` 统一映射新消息及历史消息，是接显示格式的合适位置。
- 回复来源不止大模型：通用回复、软便双层回复、规则追问、风险提示、产品比较、提醒确认、资料不足和离线兜底都有独立输出路径。
- 仅修改 `_generate_answer` 的提示词，会遗漏规则分支和软便分支；仅修改前端，也不能可靠判断一句话究竟有利还是风险。

### 建议怎么做

1. **统一最小展示协议**：保留原 `reply/content` 文本与现有交互字段，新增可选 `display_blocks`。每块含 `kind`（正文、有利、不利、观察）和文本片段，片段支持 `strong`；只有可信后端输出可指定这些样式，不接收任意 HTML/CSS。前端对旧消息继续显示纯文本，必要时在可信助手内容中支持有限的 `**...**` 兼容解析。
2. **后端负责语义**：规则回复在原业务规则处标注类型；模型回复使用有限结构并校验，失败则退回已有文本，不额外再调用一个模型给全文“美化”。有证据的优点用 ✅，明确的不利点用 ❌，不确定性/观察项用 ❗。资料缺失不能标成已确认不利。
3. **前端负责排版**：用嵌套 text/view 组件显示加粗、段间距及分点，保留文本复制。主回复、候选粮特点、需留意项及风险提示统一呈现；用户原话不套用助手的语义标记。
4. **控制密度**：优先结论，再放取舍和动作；每段建议 1–2 句话，同段只强调关键短语。短追问保持简短，不要求每条回复凑齐三个 emoji 或固定章节。长度只是展示指导，不截断风险信息。
5. **覆盖历史及异常**：历史消息、模型超时兜底、资料不足、带选项的追问和风险分流都需要检查，不能破坏 `response_type`、`interaction.slot/value`、候选选择和提醒确认。

例如，仅在后端确有相关比较证据时：

> ✅ **结构接近**：候选粮与参考粮的蛋白来源相近。  
> ❌ **脂肪负担较高**：不符合这次优先降低脂肪负担的目标。  
> ❗ **继续观察**：记录食欲和便便变化；出现原有规则提示的异常时及时处理。

## 5. 开发顺序与验收

建议分成三个可独立验收的交付：先做 18 的可靠执行和状态，再接 19 的完成事件及通知；20 独立开发。18 的状态设计同时预留 21 的不完整结果与二次更新。

| --- | --- | --- | --- |
| 18 自动处理 | worker、原子认领、租约/重试、过期回报校验、状态同步、市场重建排队 | 进程托管、状态与失败原因显示 | 不打开管理页仍可执行；同任务各节点依赖串行；多个 worker 不重复认领；中断可恢复；重放及撤销安全；待人工复核可恢复；积压不饿死新任务 |

## 6. 本轮实施结果（2026-10-16）

再次回读需求池，18、19、21 的模块均为“我的食物→狩猎广场→投稿”，只有 20 直接归于 AI 管家。21 服务于 18 的不完整原料计算及二次更新；这些结果可能被管家消费，但不能把四条都归为聊天模块。

用户允许暂缓有不确定性的 21，因此本轮不放行不完整评分。待明确缺失原料如何参与各指标的分母、原料位置权重、无有效输入时的处理、部分结果如何与完整市场排名隔离，再实现两阶段计算。现有覆盖率与缺失项继续保留；不以跳过 gate 冒充完成 21。

18 已增加专用后台执行器：提交成功后唤醒，默认单任务并发，60 秒补扫；从 MySQL 原子认领节点，记录执行令牌、次数和下次重试时间，保持依赖顺序。限流及明确的市场重建锁忙最多自动尝试 3 次。进程中断或超时后的业务结果可能已落库，因此保留完成节点并将中断节点标为待核验，禁止盲目重放。人工核验后可从指定节点重跑。没有引入 MQ。

19 已增加私有投稿的微信订阅入口、服务端订阅记录、后台发送及结果记录、详情跳转与一次通知去重。按“首次有效结果可查看时通知一次”执行；因 21 暂缓，本轮需现有完整流水线 done 且配料有效才发出通知。OCR 识别成功不等于整个计算已完成；审核收录仍是另一状态。发送结果不确定时标为 unknown，避免盲目重发。

微信真实模板 ID、字段映射和凭据必须配置；本轮未登录管理后台选模板，也未发真实消息。配置缺失时不显示订阅入口。启用步骤、边界与验证命令见 [运行说明](submission-automation.md)。

20 已为新回复和历史助手消息生成受限的展示结构：短段落、粗体片段及明确的 ✅/❌/❗ 标记。通用及软便模型提示词共享风格要求；规则回复的风险提示和关键词也有展示路径。原文本和交互字段保留，用户消息不套用助手格式，未引入任意 HTML 渲染。

顺带修复结构标签全量重建先清空后另行写入的问题，改为同一事务删除与写入；没有重写市场排名算法，也未承诺跨三张市场产物表的同一版本原子发布。

验证：后端完整测试、既有小程序检查、新增展示/订阅检查，以及真实本地 MySQL 的并发认领、顺序执行、有限重试、中断核验、撤销、通知去重与账号隔离。业务 API 使用离线桩，未运行生产重建、真实 OCR/LLM 或微信真机通知测试。
