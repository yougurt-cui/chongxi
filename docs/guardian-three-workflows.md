# 管家换粮、选粮与提醒流程

2026-10-12。本轮在原有管家、推荐引擎与换粮事务上扩展。后端选粮和换粮通过既有聊天文字及选项工作；云端提醒需配套小程序版本发布。

## 用户交互

- 换粮：说“想换粮” → 仅补问缺失的主要诉求（减重、增重、美毛、肠道友好、黑下巴等）与当前粮 → 读取宠物档案、全部已确认历史粮与吃粮反馈 → 排除当前及历史吃过的粮 → 相似特征召回 → 结合诉求和明确反馈排序 → 展示推荐理由、营养对照和风险提示 → 选目标 → 换粮安排 → 实际开始吃后更新档案、归档原粮。
- 选粮：说“帮我选粮” → 按诉求与宠物情况给出候选；也可直接询问某款 → 展示营养数据、风险和适配理由 → 选定后先给评估 → 用户可选“制定换粮安排”或“重新推荐”。仅选中不会改当前粮。
- 年龄继续选填。无年龄不阻止推荐，说明未按年龄筛选并展示包装适用阶段。现有目录是猫粮，不能用于狗粮推荐。
- 提醒：说“明天晚上八点提醒我换水” → 识别事件、时间、重复规则 → 缺什么只问什么 → 成功保存后回复北京时间和提醒内容。无法保存时保留输入，不声称设置成功；取消未保存草稿不删除其他提醒。
- 明显新症状进入原咨询流程，高风险信号优先；“希望改善软便”保留在选粮目标流程中。

## 数据与扩展点

`guardian_food_goals.py` 集中管理目标、问法和参考权重，现有数据库配置优先。`guardian_food_analysis_service.py` 负责只读营养、风险及相似度，`guardian_recommendation_service.py` 负责筛选排序，`guardian_food_flow_service.py` 负责选择、计划和实际吃粮状态。提醒由独立对话流程调用 `miniprogram_reminder_service.py`，通知发送可后续单独接入。

相似度使用 `sku_feature_input` 的 `soft_v1` 六维量化特征（至少四维已知）；召回后才做诉求排序。当前与历史粮不受页面分页影响；产品 ID 排除对应的不同配方版本。历史明确吃粮表现用于调整参考权重；同期咨询话题只表示时间关联，不当成因果证据。

营养读取 `product_guarantee`，并以标准配方 `nutrition_json` 补充。保留单位、检测基准、保证值不等号；同名冲突值不参与对比。只有单位、基准和不等号均一致才展示保证值差异，不把它当实测含量差异。软便/黑下巴风险使用该配方最新模型结果及参考池，不输出患病概率或因果结论。

生产量化表里 `antioxidant_score` 实际是脂肪调节评分别名，不能当抗氧化证据。本轮保留真实维度来源；排名缺少抗氧化数据时去掉对应评分与依赖规则，至少覆盖配置权重的 50% 才给参考候选，返回缺失项和覆盖率。无法判断的项目明确提示；不会用默认 50 分补齐。

## 提醒与发布边界

- 新增账户隔离的云端待办及完成历史表，首次初始化时创建，创建和完成支持幂等，编辑支持版本检查，完成和下一周期同事务写入。
- 每月/每年保留原始日期锚点，月底和闰年自动处理；错过周期后跳到下一未来时间。删除保留完成历史。
- 配套小程序以云端 API 为主、本机为缓存，网络失败保留输入和缓存；账号变更后的旧响应不能覆盖新账号。旧本机提醒由用户明确导入，成功后替换，失败保留原条目。
- 新小程序在聊天 `client_context.capabilities.cloud_reminders_v1=true` 声明能力。旧版本不创建云端聊天提醒，而提示到原有页面设置，避免用户在本机列表找不到云端记录。后端可以先发布。
- 提醒仅在小程序内展示，没有接入系统推送、微信订阅消息或定时消息发送。生日同步由已保存档案读取，不信任客户端生日值。

接口字段及请求示例见 [接口文档](guardian-p0-api.md)。

## 验证

351 个后端单元测试通过；隔离 Flask/鉴权/MySQL smoke 验证选粮评估、换粮确认和档案历史事务、聊天提醒补问和落库、跨账户访问、幂等冲突、事务回滚、编辑版本、生日锚点及旧客户端消费。小程序 17 组检查通过，含云端错误保留输入、账户切换、完成历史和旧提醒导入。

生产只读数据核验：肠道、黑下巴、减重、增重、美毛和一般适配均可返回候选；换粮相似度召回、历史排除与营养对照可用。未向真实宠物档案写测试数据。真机显示与小程序发布仍由负责人验收。
