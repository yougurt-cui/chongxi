# 管家 P0：上传、吃粮历史与选粮

对应需求池第 1、5、6 项，开发分支 `feature/guardian-p0`。本次是可审查的前后端实现，尚未部署和真机验收。第 6 项仍依赖完整病历和评论经验等数据接入，不能整条标为完成。

## 可验收行为

1. 拍食品照片前明确提示包装背面的完整配料表；仅有包装正面或 source_id 不代表识别成功。API 区分 processing、unrecognized、needs_review、failed、success，返回 recognition_message、can_analyze、can_reupload。OCR 节点成功后的下游失败不改变识别成功；未完成的节点继续显示处理中。旧记录在序列化及管家入口也进行内容校验。
2. 小程序识别失败后保留品牌/产品名，重新拍照上传。没有可用配料不会进入模型分析。
3. 新增宠物级云端吃粮记录。档案保存/换粮与历史归档在同一个事务，锁定对应宠物；不重复保存相同口粮，不能把换粮计划、食品上传或推荐结果当成已经吃过的粮。手动更改名称时清除旧配方 ID。
4. 历史口粮页显示已吃过的粮，支持补录日期和表现、删除错误的历史记录。本机旧记录需核对后保存到云端，重试幂等，设备观察日期不作为实际吃粮日期。
5. 关联相同账号、相同宠物、活动会话中的同期用户咨询。日期按上海时区解释，结束日期包含当天；服务端时间保存 UTC。按健康话题统计独立会话数，每条历史最多扫描最近 1000 条消息并标注截断；缺少日期不关联，当前粮仅从服务端首次记录起关联。同期咨询不等于确诊、不适反应或因果关系。删除的会话不纳入统计。
6. 历史及话题计数进入通用管家、软便及跨流程上下文；模型上下文只带摘要，不反复发送原始咨询摘录。确认更新口粮后，后续软便轮次刷新基础饮食。
7. 选粮策略复用现有画像选择、特征派生及评分排序函数，按真实当前配方 ID 关联标准目录。只返回有适用阶段、主粮类型、配料及所需评分资料的候选；排除当前粮，遵守明确品牌、产地、每斤预算及已知过敏信息。画像权重、阈值和避让规则所需指标缺失时不使用默认中性分。
8. 候选卡展示产品、画像、匹配分和参考理由。匹配分是引擎内部参考，价格是品牌参考区间，预算按上界筛选，不是实时售价。没有年龄、适用阶段或完整数据时不给假推荐。狗及有疾病标签的宠物暂不使用猫粮库做个体推荐。
9. 推荐本身不更新档案。用户点“已开始吃这款”并确认后，通过既有档案 PATCH 校验产品/配方，更新当前粮和历史。取消、账号或宠物切换不会发起保存。软便选粮动作、历史口粮动作已接；原病历动作目前进入健康档案编辑，只编辑既有健康字段。

## API 与存储

- `GET /api/miniprogram/cat-profiles/{pet_id}/diet-history?limit=50`：含当前粮及历史，按当前粮、记录日期排序；最多 100 条，超出返回 `has_more`。
- `POST .../diet-history`：`{brand, product, started_on?, ended_on?, note?, legacy_record_id?}`，表示确认的历史吃粮，不改变当前粮。未知日期可以留空；有完整日期才关联同期咨询。旧设备 ID 按账号和宠物生成幂等记录 ID，重复确认保留第一次保存内容。
- `DELETE .../diet-history/{record_id}`：软删除历史记录；当前粮通过档案接口修改。
- 三个端点均要求 Bearer 登录态及宠物归属，忽略请求体中的 user_id。
- 新表 `miniprogram_pet_diet_history` 在首次使用时 `CREATE TABLE IF NOT EXISTS`，与现有服务初始化方式一致。无需改旧表。历史归档和档案更新在相同连接内提交；初始化在事务前独立完成。
- 新字段/识别状态均为增量接口扩展。应先部署后端，再发布配套小程序；旧前端不展示新状态指引。

## 剩余依赖与范围

- 开发库缺少完整推荐画像、评分及适用阶段等资料，已验证缺数据降级和样例排序；真实产品、LLM 输出质量和 OCR 照片效果仍需联调。
- 完整病历、抖音评论经验、B 端聚合报表和药品/玩具推荐不是本次实现。健康咨询关联不能替代完整病历。
- 不推测历史实际吃粮时间，也不把历史咨询自动用作推荐引擎的负面反馈。后续可接用户确认的吃粮耐受反馈。
- 本轮不部署，不修改生产数据库，不把需求池第 6 项整条改为完成。
